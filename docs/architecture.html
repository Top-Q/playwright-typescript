Test Automation · Architecture Overview

How the OpenProject test suite is built

One layered stack drives the product the way a user does — through a real Chromium browser — and a second, shorter path checks the same product through its HTTP API. Each layer has one job, so a change in the application touches one layer, not every test.

The layers

Read top to bottom: each layer calls only the one beneath it. A test never sees a CSS selector; a page object never decides whether something passed.

LAYER 01
Test cases
Business intent, in business language

Each test is written as Given / When / Then steps that a product owner can read. The step names are what appears in the report when a run fails, so a failure is legible without opening code.

  • Invite a new member via email and verify they appear in the members list @ui @members
  • Change a member role from Member to Project admin @ui @regression
  • Assign a work package to a current project member @ui @workpackage
  • Create a one-time meeting and verify it appears on the meetings list @ui @meetings
  • Delete work package (phase) @ui @regression
  • Create a work package via the REST API @api
▼ calls page objects · asserts with expect()
LAYER 02
Fixtures
Preconditions, set up once and reused

Shared setup lives in Playwright fixtures rather than being repeated in every test. A test that needs a logged-in admin already inside the Demo project simply asks for readyOverviewPage and starts at its first business step. Fixtures also own teardown, so tests leave the system as they found it.

▼ hands the test a ready page object
LAYER 03
Page objects & components
The only place that knows the UI

One class per screen, one component class per reusable region. All of them extend a shared base that guarantees a waitForLoad() contract, and navigation methods return the next page object — so a test reads as a chain of screens. When OpenProject changes a screen, exactly one class changes.

LAYER 04
Playwright engine
Locators, waiting, evidence

Playwright resolves each locator at the moment of use and waits for the element to be actionable, which removes the fixed sleeps that make older suites flaky. Every run records a trace, a video and a screenshot per action, so a failure is diagnosed from the recording instead of by re-running it.

LAYER 05
Transport
How the suite reaches the product

The UI path speaks the Chrome DevTools Protocol to a real Chromium instance. The API path speaks plain HTTPS to the same application's REST endpoint. Both end at the same deployed OpenProject, which is what makes the two kinds of test comparable.

How Playwright talks to the browser

There is no plugin installed in the browser and no remote grid in the middle. The test process opens a single WebSocket to a Chromium instance and speaks the Chrome DevTools Protocol — the same protocol the browser's own developer tools use.

Solid lines are commands going out; the dashed line is the browser reporting back. Because that return channel carries DOM state and screenshots, the same connection that drives the test also produces the evidence attached to a failure.

Waiting is decided by the browser

The browser reports when an element is actually clickable, so tests do not guess with timers. This is the single biggest source of stability compared with older tooling.

Network is visible and controllable

Requests the page makes can be observed or intercepted from the test — useful for isolating a UI defect from a backend one.

A live session can be inspected

Engineers attach to a paused run over the same protocol to step through it and read the page, which shortens the diagnosis of a new failure.

No agent to install

The browser is launched by the test run itself. Nothing is installed into the product or the environment under test.

Two levels of coverage, one product

UI tests prove the product works for a person. API tests prove the rules hold at the service boundary — and run fast enough to cover many more cases.

UI tests

Full user journeys through the real interface: invite a member, change a role, create and delete a work package, schedule a meeting. Slower, and the closest thing to a customer's experience.

HTTP API tests

The same fixture pattern, one layer shorter: no page objects, a fluent client instead. Used for data setup, for cases that are impractical through the UI, and to pin the contract other systems integrate against.
